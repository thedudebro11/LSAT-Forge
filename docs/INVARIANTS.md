# LSAT Forge — System Invariants

These are non-negotiable facts about the system. Violating any of them will cause bugs
that are difficult to trace. Read this before editing auth, billing, database, or routing code.

---

## 1. Identity: `profiles.id` equals `auth.users.id`

The `profiles` table uses the Supabase `auth.users.id` UUID as its **primary key** — not a
separate `user_id` column. Every RLS policy and every query must use `id`, not `user_id`.

```sql
-- CORRECT
.eq('id', user.id)

-- WRONG (column does not exist on profiles)
.eq('user_id', user.id)
```

This is enforced by `references auth.users(id) on delete cascade`.

---

## 2. Tier values are `'free'`, `'monthly'`, `'annual'` — never `'pro'`

The DB check constraint in `supabase/schema.sql` is:

```sql
check (tier in ('free', 'monthly', 'annual'))
```

The original product spec (`lsat-specs/02-DATA-MODEL.md`) incorrectly listed `'pro'` as a tier
value. **That value will fail the DB constraint and silently no-op the UPDATE.** Any code that
writes `tier: 'pro'` is wrong.

**Critical impact:** The Stripe webhook spec in `lsat-specs/05-STRIPE.md` sets `tier: 'pro'`
on `checkout.session.completed`. That code **must not be used as written**. The correct
implementation must set `tier: 'monthly'` or `tier: 'annual'` based on which Stripe price ID
was purchased:

```typescript
// In stripe-webhook Edge Function — checkout.session.completed handler
const priceId = subscription.items.data[0].price.id
const tier = priceId === Deno.env.get('STRIPE_ANNUAL_PRICE_ID') ? 'annual' : 'monthly'

await supabase.from('profiles').update({ tier, ... }).eq('id', userId)
```

## 3. `isPro` requires BOTH conditions — either alone is insufficient

```typescript
// src/context/AuthContext.tsx
const isPro =
  !!profile &&
  profile.tier !== 'free' &&          // has a paid tier
  profile.subscription_status === 'active'  // AND subscription is currently active
```

A user with `tier: 'monthly'` and `subscription_status: 'canceled'` is **not Pro**. A user with
`subscription_status: 'active'` and `tier: 'free'` is **not Pro**. Both conditions must pass.

This logic lives in `AuthContext` and must not be simplified elsewhere.

**Related: `isLoading` tracks session state only.** AuthContext exposes `isLoading: boolean` which
reflects Supabase session loading state. **This does not include profile loading.** Background
profile refreshes (e.g., after Stripe webhook, subscription updates) do not trigger a full-page
spinner. This prevents UX flicker during normal operations. The `fetchProfile` function uses
try/finally to guarantee `setProfileLoading(false)` runs even on error, preventing permanent
spinner state.

---

## 4. Free tier cap is 20 questions, lifetime, enforced server-side

The `questionsRemaining` value in `AuthContext` is:

```typescript
Math.max(0, 20 - (profile?.questions_used ?? 0))
```

This is a **display value only** — it drives the banner UI. The actual enforcement happens in
the `generate-questions` Edge Function:

```typescript
if (profile.tier === 'free' && profile.questions_used >= 20) {
  return new Response(JSON.stringify({ error: 'FREE_LIMIT_REACHED' }), { status: 403 })
}
```

Never gate question generation on the client-side value alone. A user could bypass it by
manipulating React state. The server is the source of truth.

---

## 5. Questions are never stored in the database

Sessions and responses are persisted. The question text, stimulus, choices, and explanation
generated by the Anthropic API are **never written to the DB**. They live in React component
state for the duration of the session.

The `generate-questions` Edge Function creates a `sessions` row (to track the session exists)
and returns the questions to the frontend. Only the user's answer choices and correctness are
written back via `complete-session`.

Do not add a `questions` table without rethinking the entire data model and AI cost model.

---

## 6. `type_stats` is written only by the `update_type_stats()` SQL function

The `type_stats` table is a pre-aggregated rollup. It must **only** be written via the
`update_type_stats(p_user_id, p_session_id)` Postgres function. That function uses
`INSERT ... ON CONFLICT DO UPDATE` with proper cumulative math.

Writing directly to `type_stats` from Edge Functions or the frontend will corrupt the
aggregates. The function is idempotent (safe to call multiple times for the same session).

## 7. Provider nesting order is fixed

```tsx
// src/main.tsx
<QueryClientProvider client={queryClient}>       // 1. outermost
  <SessionContextProvider supabaseClient={supabase}>  // 2. Supabase session
    <App />                                       // 3. contains AuthProvider + BrowserRouter
  </SessionContextProvider>
</QueryClientProvider>
```

```tsx
// src/App.tsx
<BrowserRouter>
  <AuthProvider>   // 4. reads useUser() from SessionContextProvider above
    <Routes>...
```

`AuthProvider` calls `useUser()` and `useSessionContext()` from `@supabase/auth-helpers-react`.
These hooks require `SessionContextProvider` to exist somewhere above them in the tree.
Swapping this order causes a runtime error.

---

## 8. The Stripe webhook is the single source of truth for billing state

Profile `tier` and `subscription_status` are **never** updated by the frontend or by the
`create-checkout-session` Edge Function. They are updated only by the `stripe-webhook`
Edge Function in response to Stripe events:

| Stripe event                       | What it sets                                  |
|------------------------------------|-----------------------------------------------|
| `checkout.session.completed`       | `tier`, `stripe_subscription_id`, `subscription_status: 'active'` |
| `customer.subscription.updated`    | `subscription_status`, `subscription_period_end` |
| `customer.subscription.deleted`    | `tier: 'free'`, `subscription_status: 'canceled'` |
| `invoice.payment_failed`           | `subscription_status: 'past_due'`             |

After a successful checkout, the frontend shows `/success` and calls `refreshProfile()`.
The profile fetch will show updated state only after the webhook has fired and updated the DB.
There can be a 1-3 second race window — handle it gracefully (show a loading state, not an error).

**Deployment requirement:** The `stripe-webhook` Edge Function MUST be deployed with the
`--no-verify-jwt` flag because Stripe sends no Supabase JWT. Without this flag, the Supabase
gateway rejects all webhook requests with 401:
```bash
npx supabase functions deploy stripe-webhook --project-ref <ref> --no-verify-jwt
```

## 9. Route protection has two independent layers

**Client-side** (UX): `ProtectedRoute` redirects unauthenticated users to `/login` and
non-pro users to `/upgrade`. This is cosmetic — fast, good UX, but bypassable.

**Server-side** (enforcement): Every Edge Function verifies the Supabase JWT and re-checks
tier/limit before doing anything. The client-side guard can be removed and the app remains
secure because of server enforcement.

Do not remove server-side checks in Edge Functions on the assumption that the frontend guards
are sufficient.

---

## 10. `subscription_status` values come from Stripe, not from a fixed enum

Stripe can emit statuses like `'active'`, `'canceled'`, `'past_due'`, `'trialing'`,
`'incomplete'`, `'incomplete_expired'`, `'unpaid'`. The DB column is plain `text` with no
check constraint. Only `'active'` grants Pro access (`isPro` check above). All other values
are treated as non-Pro.

Never add a `CHECK` constraint to `subscription_status` — Stripe may introduce new statuses.

---

## 11. The anon key is safe to expose; the service role key is not

```
VITE_SUPABASE_URL=...       ← bundled into the browser JS, fine
VITE_SUPABASE_ANON_KEY=...  ← bundled into the browser JS, safe (RLS enforces access)

SUPABASE_SERVICE_ROLE_KEY=... ← only in Edge Function secrets, NEVER in VITE_ vars
ANTHROPIC_API_KEY=...          ← same — Edge Function only
STRIPE_SECRET_KEY=...          ← same
```

The service role key bypasses all RLS. If it reaches the browser, any user can read and write
any row in the database.
